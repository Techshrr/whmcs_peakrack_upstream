# PeakRack Upstream WHMCS Integration Design

Status: Approved design, pending implementation plan

Date: 2026-06-05

Official repository: https://github.com/Techshrr/whmcs_peakrack_upstream

## 1. Objective

Build a source-available WHMCS-to-WHMCS integration for reseller provisioning.
The system consists of:

1. An upstream WHMCS Addon Module that exposes a custom authenticated API,
   manages reseller policies, consumes WHMCS client Credit, and coordinates the
   upstream products' existing Provisioning Modules.
2. A downstream WHMCS Provisioning Module that calls the upstream API and maps
   the upstream services into downstream WHMCS products and services.

The first release is `v1.0.0`.

## 2. Confirmed Product Decisions

- Target WHMCS version: `9.0.x`.
- Target PHP version: `8.2+`; PHP 8.3 is the primary development runtime.
- PHP 8.2 and 8.3 are the initial CI targets. A higher PHP version is supported
  only when WHMCS 9.0.x supports it and the project validates it.
- Source is distributed as readable PHP. ionCube is not part of source
  development.
- The upstream is WHMCS with a custom open API, not the standard external WHMCS
  API.
- Reseller ownership model:
  - One API key represents one downstream WHMCS instance.
  - Each API key binds to one upstream reseller client and one permanent
    `instance_id`.
  - The downstream's end-customer identity is not synchronized upstream.
- Billing uses the bound upstream client's native WHMCS Credit balance.
- Each API key has an explicit product, billing-cycle, and parameter whitelist.
- Provisioning uses a mixed synchronous and asynchronous idempotent workflow.
- Creation failures that are confirmed before successful delivery are
  compensated by restoring the exact Credit consumed.
- Cancellation and termination do not automatically refund Credit.
- Renewal is API-driven.
- Client Area functionality is read-only service information plus optional SSO.
- Product parameters use upstream-managed whitelist mappings.
- Service delivery fields use configurable generic mappings.
- Downstream service status synchronization is pull-based.
- Package changes use WHMCS's native upgrade and downgrade process.
- Upstream transactional emails generated by API-managed operations are
  suppressed.
- The upstream and downstream modules are maintained in one repository.
- The public API uses an Addon-local entry point.
- The API uses HMAC-SHA256 request signing.
- Both upstream and downstream background processing use independent CLI Cron
  scripts.
- `WHMCS\Database\Capsule` is allowed because it is bundled with WHMCS.
- The project uses Apache-2.0 because it is an infrastructure integration.

## 3. Scope

### 3.1 Included

- Upstream Addon activation, schema installation, admin interface, API entry
  point, task worker, API key management, product policy management, operation
  audit, service registry, and system health checks.
- Downstream Provisioning Module functions for connection testing, creation,
  suspension, unsuspension, termination, renewal, package change, Client Area,
  and service SSO.
- Native WHMCS Credit billing, order, invoice, upgrade, cancellation, and module
  actions through WHMCS Local API calls.
- Idempotency, replay protection, rate limiting, retries, compensation, and
  manual-review states.
- English and Simplified Chinese language files.
- Readable source distribution, release documentation, tests, and release
  packaging.

### 3.2 Not Included in v1.0

- End-customer synchronization to the upstream WHMCS.
- A separate reseller wallet or multi-currency Credit balance.
- Currency conversion.
- Upstream-to-downstream Webhooks.
- Customer-controlled suspend, unsuspend, terminate, or package-change buttons.
- Automatic refunds after a successfully delivered service is cancelled or
  terminated.
- Direct passthrough of arbitrary upstream Custom Fields or Configurable
  Options.
- ionCube packaging.
- Support for upstream products without a Provisioning Module.

## 5. Runtime Architecture

### 5.1 Upstream Addon Module

The Addon Module:

- Creates and migrates Addon-owned tables.
- Manages API keys, encrypted API secrets, IP allowlists, rate limits, reseller
  client bindings, and permanent instance UUIDs.
- Manages product policies and parameter mappings.
- Exposes the signed JSON API.
- Uses WHMCS Local API calls to create and manage upstream orders, invoices,
  services, Credit, upgrades, cancellation requests, and Provisioning Module
  actions.
- Stores service bindings, idempotent operations, retry state, and sanitized
  audit events.
- Runs a one-minute CLI worker for unfinished operations.
- Guards API-managed upstream services from independent upstream WHMCS
  automation module actions.

### 5.2 Downstream Provisioning Module

The Provisioning Module:

- Implements the WHMCS Provisioning Module entry functions.
- Maps downstream product and service parameters into the versioned upstream
  API contract.
- Signs requests and validates responses.
- Saves upstream identifiers and cached delivery data into service properties.
- Keeps the downstream service `Pending` until the upstream confirms delivery.
- Runs a five-minute CLI synchronization job.
- Shows only filtered cached service information and optional SSO in the Client
  Area.

### 5.3 Trust Boundaries

- The upstream WHMCS is authoritative for Credit, orders, invoices, upstream
  service records, and actual resource state.
- The downstream WHMCS is authoritative for its end-customer relationship,
  downstream billing, and the local service ID.
- The API key and its permanent `instance_id` define the downstream instance.
- The pair `api_key_id + local_service_id` defines service ownership upstream.
- The bound reseller client ID and `instance_id` cannot be changed after an API
  key is created.
- Secret rotation updates the secret on the same API key record, preserving
  instance identity and service bindings.

## 6. Installation Preconditions

### 6.1 Upstream WHMCS

- WHMCS `9.0.x`.
- PHP `8.2+`.
- HTTPS with a valid certificate.
- WHMCS Credit system enabled.
- `Automatic Credit Use` disabled.
- `Credit on Downgrade` disabled.
- A configured non-capturing order payment method. The Addon default is
  `mailin`, but the administrator must select a valid installed payment method.
- A dedicated reseller client account for each reseller relationship. The
  account should not be exposed as a general upstream Client Area login.
- Authorized upstream products must:
  - exist,
  - have a valid price for the reseller client's currency and authorized cycle,
  - be assigned to a Provisioning Module,
  - not rely on arbitrary end-customer input that the policy cannot map.
- A one-minute Cron entry for the Addon worker.

### 6.2 Downstream WHMCS

- WHMCS `9.0.x`.
- PHP `8.2+`.
- HTTPS access to the upstream API.
- A separate API key for the downstream instance.
- A five-minute Cron entry for service synchronization.

The upstream System Health page treats enabled `Automatic Credit Use` or
`Credit on Downgrade` as blocking configuration errors.

Addon activation rejects PHP versions below 8.2 and WHMCS versions outside the
9.0.x target. It preserves existing Addon-owned data on deactivation.

## 7. Upstream API

### 7.1 Entry Point

```text
/modules/addons/peakrack_upstream_api/api/v1/index.php
```

The entry point loads the WHMCS runtime, accepts JSON only, and does not require
a WHMCS browser session. It does not modify WHMCS root or core files.

The API does not follow redirects. It returns JSON for every handled response.

### 7.2 Endpoints

```text
GET  /health
GET  /catalog
POST /services
GET  /services/{local_service_id}
POST /services/{local_service_id}/suspend
POST /services/{local_service_id}/unsuspend
POST /services/{local_service_id}/terminate
POST /services/{local_service_id}/renew
POST /services/{local_service_id}/change-package
POST /services/{local_service_id}/sso
GET  /operations/{operation_id}
```

All endpoints, including `/health`, require valid HMAC authentication.
`/catalog` returns only the authenticated key's authorized products, cycles,
and standard parameter identifiers.

### 7.3 Authentication Headers

```text
X-PeakRack-Key
X-PeakRack-Timestamp
X-PeakRack-Nonce
X-PeakRack-Signature
Idempotency-Key
Content-Type: application/json
```

`Idempotency-Key` is required on every write endpoint.

### 7.4 Canonical Signature

The client signs:

```text
HTTP_METHOD
REQUEST_PATH
CANONICAL_QUERY_STRING
SHA256_REQUEST_BODY
TIMESTAMP
NONCE
```

Rules:

- HMAC algorithm: HMAC-SHA256.
- Signature encoding: lowercase hexadecimal.
- Request body hash: SHA-256 of the exact raw request bytes.
- Query keys and values: RFC 3986 encoding, sorted by key then value.
- Timestamp: Unix seconds.
- Default allowed clock skew: 300 seconds.
- Nonce uniqueness: enforced per API key with a database unique index.
- Signature comparison: `hash_equals()`.
- API secrets: stored using WHMCS reversible encryption and shown only once at
  creation or rotation.

The upstream stores accepted nonces long enough to exceed the allowed clock
window, then removes expired nonce records in the worker.

### 7.5 Response Envelope

```json
{
  "success": true,
  "status": "completed",
  "data": {},
  "operation_id": "uuid",
  "error": null
}
```

Operation status values:

```text
queued
processing
completed
failed
manual_review
```

Standard service status values:

```text
pending
provisioning
active
suspended
cancellation_pending
terminated
failed
manual_review
unknown
```

Unknown upstream states map to `unknown`; they never map implicitly to
`active`.

### 7.6 HTTP Status Codes

- `200`: Successful query or completed write.
- `202`: Accepted write still processing.
- `400`: Invalid request format or signature input format.
- `401`: Authentication failure.
- `403`: IP, product, instance, or service authorization failure.
- `404`: Service or operation not found within the authenticated instance.
- `409`: Idempotency-key payload conflict or service-state conflict.
- `422`: Valid request rejected by business rules, including insufficient
  Credit or invalid product mapping.
- `429`: API key rate limit exceeded.
- `500`: Sanitized internal error.

### 7.7 Service Contract Examples

Create request:

```json
{
  "local_service_id": 123,
  "product_id": 10,
  "billing_cycle": "monthly",
  "hostname": "server.example.com",
  "password": "temporary-secret",
  "location": "hk-1",
  "os_template": "ubuntu-24.04"
}
```

The upstream never accepts a caller-selected upstream client ID, upstream
service ID, price, raw Configurable Option name, or raw Custom Field name.

Service response:

```json
{
  "success": true,
  "status": "completed",
  "data": {
    "local_service_id": 123,
    "upstream_service_id": 456,
    "upstream_order_id": 789,
    "upstream_invoice_id": 321,
    "service_status": "active",
    "operation_status": "completed",
    "primary_ip": "192.0.2.10",
    "panel_url": "https://panel.example.com/",
    "last_updated_at": "2026-06-05T12:00:00Z"
  },
  "operation_id": "uuid",
  "error": null
}
```

Dates use UTC ISO 8601. Monetary values are returned as decimal strings with
an ISO 4217 currency code. Addon-owned billing calculations do not use binary
floating point.

## 8. Identity, Idempotency, and Concurrency

### 8.1 Instance Identity

- The upstream generates a UUIDv4 `instance_id` when an API key is created.
- One API key belongs to one downstream instance.
- The same reseller client can own multiple API keys, each with a different
  `instance_id`.
- A service's global external reference is derived upstream from:

```text
instance_id:local_service_id
```

- The downstream submits only its local service ID.

### 8.2 Idempotency

- The unique constraint is `api_key_id + idempotency_key`.
- The operation also stores a canonical request hash.
- A repeated key with the same request hash returns the original operation.
- A repeated key with a different request hash returns `409`.
- The upstream persists the operation before executing side effects.

Downstream key rules:

- Create uses a deterministic key because a local service can only be created
  once.
- Renewal includes the service and target renewal boundary so the same cycle
  cannot renew twice.
- Recurring lifecycle actions generate and persist an action-specific key
  before the first request, reuse it while pending, and replace it only after a
  terminal result.
- Package-change keys include the target request hash.

### 8.3 Locking

- Operations for one upstream service execute serially.
- Credit-consuming operations for one reseller client execute serially.
- Locks are short Addon-owned database locks. The implementation must not hold
  a database transaction or core WHMCS row lock while making a network or
  Provisioning Module call.
- Side effects are coordinated by persisted operation stages and compensating
  actions, not by pretending that remote provisioning is one database
  transaction.

## 9. Upstream Data Model

The Addon owns these tables:

```text
mod_peakrack_upstream_api_keys
mod_peakrack_upstream_product_policies
mod_peakrack_upstream_services
mod_peakrack_upstream_operations
mod_peakrack_upstream_operation_events
mod_peakrack_upstream_nonces
mod_peakrack_upstream_worker_locks
```

### 9.1 API Keys

Stores:

- public API key,
- encrypted secret,
- bound reseller client ID,
- permanent instance UUID,
- enabled state,
- optional IP allowlist,
- fixed-window rate-limit settings and counters,
- last-used time and source IP,
- created and rotated timestamps.

An empty IP allowlist requires explicit administrator acknowledgement and
produces a System Health warning.

### 9.2 Product Policies

Each policy binds an API key to one authorized upstream Product ID and stores:

- allowed billing cycles,
- allowed actions,
- allowed standard Location identifiers and their upstream field mappings,
- allowed standard OS identifiers and their upstream field mappings,
- delivery-field mappings for status, primary IP, and panel URL,
- SSO permission and allowed SSO target hosts,
- `destroy` permission,
- policy enabled state.

Structured policy mappings are stored as validated JSON text. Callers never
submit arbitrary upstream field names.

### 9.3 Services

Unique key:

```text
api_key_id + local_service_id
```

Stores:

- upstream service, order, and invoice IDs,
- authorized product and billing cycle,
- standard service and operation status,
- cached primary IP and panel URL,
- last synchronization timestamp,
- current operation reference.

### 9.4 Operations

Unique keys:

```text
operation_id
api_key_id + idempotency_key
```

Stores:

- action and service reference,
- idempotency key and request hash,
- sanitized payload,
- status and stage,
- attempts and next-attempt time,
- exact Credit amount applied when relevant,
- final upstream references,
- last sanitized error code and message.

Passwords, API secrets, access tokens, signatures, and SSO URLs are never
stored in operation payloads.

### 9.5 Operation Events

Stores an append-only sanitized timeline for administrator audit. v1.0 does
not automatically purge financial and operation events. Nonce records are
purged automatically.

## 10. Operation State Machine

The common operation lifecycle is:

```text
queued
-> processing
-> completed
|-> failed
`-> manual_review
```

Create stages:

```text
accepted
-> order_created
-> invoice_verified
-> credit_applied
-> provisioning_started
-> delivery_confirmed
-> completed
```

Confirmed create failure compensation:

```text
provisioning_failed
-> compensation_pending
-> credit_restored
-> order_cancelled
-> failed
```

Unknown results remain `processing`. They are not immediately refunded or
replayed.

The API attempts synchronous completion within a configurable execution budget,
default 20 seconds. Unfinished operations return `202` and the worker continues
them. The worker defaults to 12 attempts with exponential backoff capped at 60
minutes. Exhausted or unsafe operations become `manual_review`.

## 11. Billing and Lifecycle Flows

### 11.1 General Billing Rules

- The reseller client's upstream WHMCS currency is the only billing currency.
- Products without valid authorized pricing in that currency are rejected.
- The caller cannot override price or currency.
- The Addon uses WHMCS Local API calls rather than direct writes to core order,
  invoice, Credit, transaction, or service tables.
- API-generated order, invoice, payment, and welcome emails are suppressed.
- The exact Credit amount applied is stored on the operation and reused for any
  eligible compensation. It is never recalculated later.

### 11.2 Create Service

```text
Validate key, policy, cycle, currency, hostname, and mapped parameters
-> acquire reseller billing lock
-> precheck product base price and current Credit
-> AddOrder with noemail/noinvoiceemail and a configured payment method
-> read the final generated invoice balance
-> if Credit is insufficient, cancel the order and invoice without provisioning
-> ApplyCredit with noemail
-> AcceptOrder without customer email and execute the upstream module
-> read mapped delivery fields
-> complete, continue processing, or compensate a confirmed failure
```

The final invoice is authoritative because tax and WHMCS pricing rules may
change the amount after order creation. Insufficient Credit may therefore leave
cancelled order and invoice audit records, but it must not leave a Credit debit
or provisioned resource.

The password is accepted only in the initial create request. Before returning a
`202`, the operation must have created the upstream service record so WHMCS can
store the password in its encrypted service field. The operation queue and
audit events never store it. The worker reads it from the upstream WHMCS
service only when the Provisioning Module requires it.

### 11.3 Renew Service

```text
Validate service ownership and authorized cycle
-> acquire reseller billing lock
-> locate an existing unpaid renewal invoice for the service and due boundary
-> otherwise create an on-demand service renewal using AddOrder servicerenewals
-> read the final invoice balance
-> ApplyCredit with noemail
-> allow the normal WHMCS renewal/module flow
-> confirm the next due date advanced exactly once
```

The existing renewal invoice lookup prevents the upstream WHMCS Cron and the
API from creating duplicate renewal invoices.

### 11.4 Change Package

- The target product, cycle, Location, and OS must be authorized by policy.
- The Addon uses `UpgradeProduct` to calculate and create the native WHMCS
  upgrade or downgrade order.
- Positive invoice balances are paid with Credit before the package change is
  confirmed.
- `Credit on Downgrade` must remain disabled, so a downgrade does not add
  prorated Credit to the reseller.
- A package change with an unexpected negative-credit effect becomes
  `manual_review` instead of modifying Credit automatically.
- The operation confirms the resulting product and module state before
  completion.

### 11.5 Suspend and Unsuspend

- Use the upstream service's Provisioning Module through `ModuleSuspend` and
  `ModuleUnsuspend`.
- Do not create billing records.
- Treat an already-achieved target state as idempotent success.

### 11.6 Terminate

- `cancel_only` creates an end-of-term cancellation request and does not
  immediately execute the termination module.
- The Addon worker tracks the authorized `cancel_only` request and runs the due
  termination in an authorized operation context at the service's end date.
- `destroy` immediately calls `ModuleTerminate` and marks the service
  terminated only after confirmation.
- `destroy` requires both downstream product configuration and upstream product
  policy permission.
- Neither mode automatically refunds Credit.

### 11.7 Confirmed Create Failure Compensation

- Compensation is allowed only when the service was never confirmed delivered.
- Restore the exact applied Credit through the WHMCS `AddCredit` Local API with
  an operation-specific description.
- Cancel the related order and invoice through supported WHMCS actions.
- A unique compensation stage prevents duplicate restoration.
- Failed or ambiguous compensation becomes `manual_review`.
- No code directly edits the client's Credit balance.

## 12. Upstream Automation Guards

The upstream Addon `hooks.php` protects API-managed upstream services from
independent module actions triggered by upstream automation:

- `PreModuleSuspend`
- `PreModuleUnsuspend`
- `PreModuleTerminate`
- `PreModuleRenew`
- `PreModuleChangePackage`

For a service present in `mod_peakrack_upstream_services`, these hooks abort a
module action unless it is running inside an Addon-authorized operation
context. This prevents the upstream Cron from independently changing an
API-managed service while preserving automation for unrelated upstream
services.

The Addon's own worker establishes the authorized request-scoped operation
context immediately before calling the WHMCS Local API, including invoice
payment that can trigger a module renewal or package change. The context is
never accepted from an HTTP request parameter.

The hooks do not alter WHMCS core files and do not block invoice generation.
Renewal logic explicitly finds and pays existing renewal invoices.

## 13. Product and Delivery Mapping

The downstream submits standard identifiers such as:

```text
location: hk-1
os_template: ubuntu-24.04
```

The upstream product policy maps each allowed standard value to a controlled
upstream Configurable Option or product Custom Field value. Unknown values and
unknown request keys are rejected.

Delivery mappings can read only configured safe sources:

- WHMCS service status,
- WHMCS Dedicated IP,
- explicitly selected admin-safe product Custom Fields,
- a configured HTTPS panel URL field.

The policy cannot expose passwords, tokens, secrets, private notes, or arbitrary
Custom Fields.

SSO is enabled only when:

- the product policy allows SSO,
- the upstream Provisioning Module supports `ServiceSingleSignOn`,
- the generated URL is HTTPS,
- the target host matches the policy allowlist.

SSO URLs are generated per request and are never cached or logged.

### 14.2 Implemented Functions

### 14.3 Server Configuration Mapping

```text
Hostname    -> upstream API hostname
Use SSL     -> required
Port        -> default 443
Username    -> API Key
Password    -> API Secret
Access Hash -> upstream WHMCS base path, not a secret
```

The module builds:

```text
https://{hostname}:{port}/{base-path}/modules/addons/peakrack_upstream_api/api/v1
```

The path is normalized and cannot contain a URL authority, query string, or

### 14.4 Product Configuration

```text
Upstream Product ID
Upstream Billing Cycle: auto / explicit cycle
Upstream Location
Default OS Template
Terminate Mode: cancel_only / destroy
Request Timeout
```

Defaults:

- Request Timeout: 30 seconds.
- Allowed Request Timeout range: 5 to 120 seconds.
- Terminate Mode: `cancel_only`.
- Upstream Billing Cycle: `auto`, which maps the downstream service billing
  cycle to the same authorized upstream cycle.

`Debug Mode`, `Auto Suspend`, and `Auto Terminate` are omitted. WHMCS Module Log
controls logging, and downstream WHMCS Automation Settings control downstream
lifecycle calls. The upstream still validates every product setting against
the API key's product policy.

### 14.5 Service Properties

Admin-only service properties:

```text
Upstream Service ID
Upstream Order ID
Upstream Invoice ID
Upstream Operation ID
Upstream Status
Upstream Panel URL
Provisioning Error
Last Sync Time
Current Idempotency Key
```

The primary IP is written to the WHMCS core Dedicated IP field. Core service
status changes and Dedicated IP updates use supported WHMCS APIs or models,
not ad hoc core table writes.

### 14.6 CreateAccount Behavior

- Refuse duplicate creation when an upstream service binding already exists.
- Persist the create idempotency key before the first request.
- Return `success` only after confirmed upstream delivery.
- On `processing`, save the operation ID and return an administrator-readable
  processing message so the downstream service remains `Pending`.
- The downstream sync Cron changes the local service to `Active` only after the
  upstream reports confirmed delivery.

### 14.7 Client Area and SSO

The Client Area shows only:

- standard service status,
- primary IP,
- panel URL,
- last synchronization time,
- SSO action when available.

It uses theme-neutral Smarty-compatible markup. It does not receive API
credentials, upstream invoice/order IDs, operation errors, or internal
operation IDs.

The Client Area reads cached information. When cache is stale, it may attempt a
short upstream query, but a failed query must not block the page or discard the
last known safe data.

## 15. Background Jobs

### 15.1 Upstream Worker

Path:

```text
/modules/addons/peakrack_upstream_api/cron/worker.php
```

Schedule: every minute.

Responsibilities:

- Claim due operations with a lock.
- Continue processing and verify unknown outcomes.
- Execute due `cancel_only` terminations in an authorized operation context.
- Run safe retries and compensation.
- Move exhausted or unsafe operations to `manual_review`.
- Expire nonce rows and stale worker locks.
- Update worker health timestamps.

Defaults:

- Batch size: 25.
- Single-worker lock TTL: 55 seconds.
- Maximum attempts: 12.
- Backoff cap: 60 minutes.

### 15.2 Downstream Sync

Path:

```text
/modules/servers/peakrackupstream/cron/sync.php
```

Schedule: every five minutes.

Responsibilities:

- Scan downstream services using `peakrackupstream` with `Pending`, `Active`, or
  `Suspended` status.
- Prioritize pending and processing services.
- Pull service and operation state.
- Update cached properties, Dedicated IP, and local service status.
- Isolate per-service errors so one failure does not stop the batch.

Defaults:

- Batch size: 50.
- Lock TTL: four minutes.
- Customer-area cache TTL: five minutes.

## 16. Upstream Admin Interface

Pages:

```text
Dashboard
API Keys
Product Policies
Operations
Services
System Health
```

### 16.1 API Keys

Administrators can:

- create a key bound to a reseller client,
- receive the generated secret once,
- configure IP allowlists and rate limits,
- disable or re-enable a key,
- rotate its secret,
- view last use time and source IP.

An API key with bound services cannot be deleted. It can only be disabled.
Neither the client binding nor instance UUID can be edited.

### 16.2 Product Policies

Administrators can:

- select authorized products and cycles,
- enable allowed lifecycle actions,
- configure standard-to-upstream parameter mappings,
- configure safe delivery-field sources,
- configure SSO and allowed target hosts,
- configure `destroy` permission.

Saving a policy validates product existence, currency pricing, and Provisioning
Module assignment.

### 16.3 Operations and Services

Administrators can:

- filter operations by API key, service, action, status, and date,
- inspect sanitized event timelines and related WHMCS records,
- safely retry or resolve `manual_review` operations,
- manually request a service-state refresh.

They cannot edit idempotency keys, applied amounts, service ownership, or
financial history.

### 16.4 System Health

System Health reports:

- WHMCS and PHP compatibility,
- HTTPS state,
- `Automatic Credit Use` state,
- `Credit on Downgrade` state,
- selected order payment method validity,
- last worker run,
- queue and manual-review counts,
- nonce cleanup health,
- API base URL,
- unsafe empty IP allowlists.

Addon deactivation preserves all data by default.

## 17. Security and Logging

### 17.1 Input and Access Control

- Reject unknown JSON fields.
- Require positive integer local service and product IDs.
- Validate billing cycle and mapped identifiers by whitelist.
- Validate hostname syntax and reject URLs, control characters, and invalid
  lengths.
- Apply a small documented maximum request-body size.
- Resolve services only through the authenticated API key and local service ID.
- Revalidate ownership and policy before every operation.
- Use CSRF tokens for Addon admin forms.

### 17.2 Network Security

- Require HTTPS.
- Verify TLS certificates and hostnames.
- Do not expose a setting to disable TLS verification.
- Do not follow API redirects.
- Use `REMOTE_ADDR` for IP allowlist checks unless an administrator explicitly
  configures trusted proxies.
- Apply a per-key fixed-window rate limit, default 120 requests per minute.

### 17.3 Recursive Redaction

The same recursive redactor is used by the upstream audit logger, upstream API
logger, downstream `logModuleCall` wrapper, and administrator views.

At minimum it redacts case-insensitive keys containing:

```text
api_key
api_secret
authorization
password
rootpw
secret
token
access_token
refresh_token
sso_url
signature
```

Raw request bodies and raw external module responses are not persisted.
Sanitization occurs before persistence, not only before display.

### 17.4 Stable External Errors

```text
AUTHENTICATION_FAILED
SIGNATURE_EXPIRED
NONCE_REUSED
RATE_LIMITED
PRODUCT_NOT_ALLOWED
INVALID_PRODUCT_MAPPING
INSUFFICIENT_CREDIT
SERVICE_NOT_FOUND
SERVICE_STATE_CONFLICT
PROVISIONING_FAILED
OPERATION_PROCESSING
MANUAL_REVIEW_REQUIRED
INTERNAL_ERROR
```

External errors never include SQL, file paths, stack traces, secrets, or raw
upstream module responses.

## 18. Testing Strategy

### 18.1 CLI Unit and Contract Tests

Without external Composer dependencies, CLI test scripts cover:

- HMAC canonicalization, signatures, timestamp expiry, and nonce replay.
- Strict input validation and unknown-field rejection.
- Recursive redaction.
- Product, currency, cycle, and parameter policy checks.
- Idempotent replay and request-hash conflict.
- Standard service-state mapping.
- Queue claiming, locks, retry backoff, and `manual_review`.
- Credit debit and compensation duplicate prevention.

### 18.2 WHMCS Integration Tests

An isolated WHMCS test installation must cover:

```text
Create API key and product policy
-> TestConnection
-> create service successfully
-> create service with processing then worker completion
-> confirmed create failure and exact Credit compensation
-> insufficient Credit and cancelled audit records
-> repeated CreateAccount without duplicate Credit or provisioning
-> suspend and unsuspend
-> renew using an existing invoice
-> renew using on-demand renewal
-> upgrade and downgrade without downgrade Credit
-> cancel_only
-> destroy
-> SSO
-> upstream automation guard hooks
-> downstream Cron synchronization
```

A mock upstream Provisioning Module supports success, confirmed failure,
timeout, and unknown-result scenarios. It is test-only and is excluded from the
production release package.

### 18.3 Compatibility and Release Tests

- `php -l` for all PHP files.
- PHP 8.2 and 8.3 CI matrix.
- WHMCS 9.0.x integration test environment.
- Source and installed-tree SHA-256 parity.
- Release-package structure validation.
- Secret and credential scanning.
- UTF-8 documentation rendering checks.
- Manual live compatibility validation against at least one real upstream
  Provisioning Module before claiming provider compatibility.

## 20. Acceptance Criteria

The v1.0 implementation is acceptable when:

1. Both modules install without modifying WHMCS core or root files.
2. The upstream Addon blocks activation on incompatible WHMCS and PHP versions.
3. System Health identifies unsafe Credit settings and missing workers.
4. Valid signed requests work and invalid signatures, stale timestamps, reused
   nonces, and unauthorized service access are rejected.
5. Product and parameter policies prevent unauthorized purchasing or field
   passthrough.
6. Create, renew, package change, suspend, unsuspend, cancel, destroy, query,
   and SSO follow the documented authorization and idempotency rules.
7. A repeated logical operation cannot duplicate provisioning, Credit debit, or
   eligible compensation.
8. Unknown provisioning outcomes remain processing until confirmed or moved to
   manual review.
9. The downstream service remains Pending until upstream delivery is
   confirmed.
10. Client Area output contains no upstream secrets, financial references, or
    internal errors.
11. Logs and persisted events are recursively redacted before storage.
12. Upstream automation guards prevent independent module lifecycle actions on
    API-managed services.
13. All automated tests, PHP lint, packaging checks, parity checks, and secret
    scans pass.
14. Remaining real-provider compatibility limits are explicitly documented.
